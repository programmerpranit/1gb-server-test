Summary

No measurable gain over v02. By the capacity rule (highest passing level) v04 scores 1400 VUs at 660 req/s, but that pass is marginal (p95 788 ms, 1.5 % under 800; p99 991 ms, 1 % under 1000), and the lower levels 1300 and 1350 VUs both failed. Read the capacity as "about 1300–1400 VUs, 540–660 req/s", the same band as the parent tag (v02, pool 10: 1350 VUs / 619 req/s). 1500 VUs fails (614 req/s, p95 1316 ms). 0 % errors everywhere.

  • The change works as designed, but the effect is smaller than the run-to-run noise at the ceiling. Like, unlike and comment now take 1 round trip instead of 4. That removes about 30 % of all queries (≈ 1.6 → ≈ 1.1 per request across the action mix). db p95 dropped a little (30–38 ms vs. 37–48 ms in v02 at the same levels).
  • The CPU split did not change: Node ≈ 42 % / Postgres ≈ 50 %, CPU at 99.5–100 % at every level. The removed queries were the cheapest ones (BEGIN, COMMIT, and short single-row updates), so the saving per request is small.
  • At 100 % CPU, the outcome is decided by whether a queue forms during the ramp, not by the code. Over the four shared levels v04 averages 597 req/s and v02 584 req/s (+2 %), while single runs of either tag swing ±60 req/s. v04 passed 1400 but failed 1300 and 1350; v02 passed 1300 and 1350 but failed 1400.
  • Memory is not a constraint. Peak 516 MB used (445 MB still available), Node ≤ 136 MB, Postgres ≤ 127 MB, no swap.
  • The runs are clean. CPU never dropped below 70 % during any hold phase, steal ≤ 0.6 %, the load generator averaged 19–21 % CPU, and app_log_tail.txt has no errors.
  • Kept as the parent of the next tag: it is correct, atomic, does no harm, and lowers db time slightly.
  • Next: prepared statements (pg named queries) to skip parse/plan in Postgres, which uses half the CPU. To see small gains, also compare at a level below saturation (e.g. 1000 VUs, where v02 used 84 % CPU for 538 req/s): the CPU cost per request is measurable there, unlike at the ceiling.

What changed vs. the previous tag

Parent: node-express-v02-pool (pool 10). v03 (pool 20) was worse and is not carried forward. One change: the writes that touch two tables are now one SQL statement with data-modifying CTEs instead of BEGIN / 2 queries / COMMIT:

  • like: INSERT INTO likes ... SELECT FROM posts WHERE id = $1 ON CONFLICT DO NOTHING, then UPDATE posts SET like_count = like_count + 1 only for the inserted row; the count comes from the UPDATE or, for an existing like, from posts.
  • unlike: DELETE FROM likes ... RETURNING, then decrement only for the deleted row.
  • comment: INSERT INTO comments ... RETURNING, then UPDATE posts SET comment_count = comment_count + 1.

A single statement is one transaction, so the writes stay atomic. Responses and status codes are unchanged (verified: new/repeat like and unlike, unknown post 404, unknown user 401, empty text 400). A concurrency check of 30 parallel likes by one user, 40 by different users and 20 parallel unlikes left like_count = rows in likes (31).

Observations

  • Latency is still almost all pool wait: conn is 92–97 % of server time at every level. Queries themselves stay fast (db p50 12–15 ms).
  • Time outside the handler (client − server p50) is 20–26 ms, a bit above v02 (14–18 ms). With the same CPU saturation, this is likely run-to-run variation in how long requests wait for Node to be scheduled.
  • Per-endpoint p95 at 1400 VUs is uniform (716–763 ms client): every endpoint waits in the same pool queue, so the shorter write path does not show up in per-endpoint latency at saturation.
  • The k6 summary only keeps server_db overall and per phase, not per endpoint, so the write-path saving cannot be isolated from these runs. A run below saturation would show it in total CPU per request.
  • Near the ceiling, the pass/fail verdict of a single run is not reliable for changes worth less than ≈ 10 %. Future comparisons should include one unsaturated level (CPU per request) besides the edge levels.
